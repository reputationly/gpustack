## 4. 准入背压配置（现网已生效）

### 4.1 机制

`gpustack/routes/videos.py::_check_admission` 在提交时估算排队时间，超阈值直接 429：

```
est_wait = floor(该模型非终态任务数 / 运行实例数) × latency
est_wait > queue_wait  →  429「系统繁忙,请稍后再试 (estimated queue wait Xs > Ys)」
```

`latency` 取自 `lightx2v_model_latency_seconds`，`queue_wait` 取自
`lightx2v_model_queue_wait_seconds`；查不到才回落到按类别默认值。

### 4.2 按模型延迟(秒) `lightx2v_model_latency_seconds`

值 = 实测**热态**单实例执行耗时（已剔除每实例首单的一次性冷启动，见 §5.3）。

```
ltx2.5-hd           265      qwen-image-edit      31
minimax-h3-ref2va   253      moss-voicegen        20
minimax-h3-fl2va    127      swiftvr              17
minimax-music3       84      kr2                  17
sensenova-u1.5       48      qwen-image           16
id4                  48      indextts-2.5         16
ace-step             35      hunyuan-image-3      16
                             z-image               7
```

**2026-09-02 当日两处调整**（`ltx2.5` 下线、`ltx2.5-hd` 2K 打通后）：

- **删掉 `ltx2.5` 行**（148）——模型已不存在，留着只是死行；
- **`ltx2.5-hd` 230 → 265**：它现在最慢的可用档是 2K/15s，实测引擎耗时 240~316s（n=9，中位 265）。
  延迟表按「该模型最慢玩法」取，1080P 的 131s 不能代表它；
- **`swiftvr` 13 → 17**：换到 0017–0020 新实例后复测 17.1s（5 秒 720P 源）。

### 4.3 按模型最大排队等待(秒) `lightx2v_model_queue_wait_seconds`

`queue_wait = K × latency`，K 即「每实例允许积压几单」。同步图片链路不按 K 取，
而是**对齐 new-api 侧的 QUEUED 容忍**（两道闸门任一收紧都会先失败）。

```
ltx2.5-hd           530      ace-step            140
minimax-h3-ref2va   510      moss-voicegen       100
minimax-h3-fl2va    260      swiftvr              85
minimax-music3      250      indextts-2.5         80
hunyuan-image-3     240      kr2                  60
sensenova-u1.5      145      qwen-image-edit      25
id4                 145      qwen-image           25
                             z-image              25
```

同步调整：删 `ltx2.5`（300）；`ltx2.5-hd` 460 → **530**（265×2）；`swiftvr` 65 → **85**（17×5）。

`hunyuan-image-3` 的 240 对齐 new-api 的慢模型预算
（`GPUSTACKPLUS_SLOW_IMAGE_MODELS` 命中者 `slowImageQueuedWaitSeconds=240`）；
其余同步图片模型对齐 `maxQueuedWait = 25s`。

### 4.4 行序不用管

`05cac5fb` 之后 `_lookup_by_model` 先做一趟**精确匹配**，命中即返回（线上镜像
2026-08-29 构建，已包含）。保留的子串回退只服务进度轮询器
（`videos.py:1704`，它手上只有提交时持久化的 `task.model_name`）；
准入走的是库里的权威 `model.name`。本部署没有做模型重命名，两者逐字一致，
回退根本走不到。

### 4.5 两张表如何持久化（2026-09-02 已落地：`--config-file` YAML）

`routes/config.py::set_config` 只做 `setattr` + `set_global_config`，**没有任何持久化**——
UI 上填的值只活在 server 进程内存里，容器一重建就回 `null`，全集群掉回按类别默认值。
（这就是「升级完发现配置没了」的原因。）

**现网做法**：manager 上 `/etc/gpustack/config.yaml`，只读挂进容器，启动带 `--config-file`：

```bash
docker run -d --name gpustack-server --restart unless-stopped \
  -p 80:80 \
  -v gpustack-data:/var/lib/gpustack \
  -v /nfs-output:/nfs-output \
  -v /etc/gpustack/config.yaml:/etc/gpustack/config.yaml:ro \
  <image> \
  --config-file /etc/gpustack/config.yaml
```

YAML 里两张表写成普通映射即可（`system_default_container_registry` 也一并搬进去了）：

```yaml
system_default_container_registry: quay.io
lightx2v_model_latency_seconds:
  "ltx2.5-hd": 265
  ...
lightx2v_model_queue_wait_seconds:
  "ltx2.5-hd": 530
  ...
```

优先级：**CLI 参数 > YAML 文件 > 环境变量 > 默认值**
（`cmd/start.py::parse_args`：先 `load_config_from_yaml`，再让 CLI 覆盖）。

### 4.5.1 ⚠️ 两条踩过的坑

**① 没有 `--lightx2v-model-latency-seconds` 这个命令行参数。**
它只是 `config.py:211` 的一个 pydantic 字段，`cmd/start.py` 里从未注册成 argparse 选项。
按 CLI 参数写会因无法识别而起不来。

**② 用 `-e` 传 JSON 时，别把长命令贴成折行。**
`Config` 是 `BaseSettings`（`config.py:340`，`env_prefix="GPUSTACK_"`），
所以 `GPUSTACK_LIGHTX2V_MODEL_LATENCY_SECONDS='{...}'` **机制上是可行的**，
镜像内实测能解析成 15 项 dict。但终端折行会把换行符带进单引号字符串，于是：

```
json.loads 失败: Invalid control character at: line 1 column 26
→ pydantic-settings 解码失败后把原始字符串直接交给字段
→ Config error: Input should be a valid dictionary [type=dict_type, input_type=str]
→ gpustack-prerun.sh 退出 1 → 容器崩溃重启循环 → 控制面 down
```

2026-09-02 就是这么把 server 弄挂过一次（已回滚恢复）。YAML 方案天然多行、无需转义，
不存在这个风险，**优先用 YAML**。

### 4.5.2 已改成落库（代码已就绪，待出镜像）

YAML 只解决了「启动配置」的持久化，UI 上改的仍然只活在内存里——每次升级还得回头改 YAML。
已在仓库里补上真正的落库，**下次出镜像后生效**：

| 改动 | 文件 |
|---|---|
| 新表 `runtime_configs`（`key` 唯一索引 + `value` JSON） | `gpustack/schemas/runtime_config.py` |
| 迁移 `a7c3e5d19b42`（链在 `f3a1b2c4d5e7` 之后） | `gpustack/migrations/versions/2026_09_02_1200-*.py` |
| 全新安装建表 | `gpustack/server/init_db.py` |
| `PUT /v2/config` 写库 | `gpustack/routes/config.py::_persist_runtime_config` |
| 启动时回灌 | `gpustack/server/server.py::_apply_persisted_config` |
| overlay 构建（COPY + head 断言 + py_compile） | `pack/Dockerfile.acr` |

**只有被显式改过的字段才落一行**——这是覆盖层，不是整份配置的快照。
没有行的字段照常走 CLI / YAML / env 的老链路，密钥类字段永远不会被抄进库
（`WHITELIST_CONFIG_FIELDS` 里本来就没有 `jwt_secret_key` / `bootstrap_password` /
`huggingface_token`，有测试守着）。

**优先级：库里的覆盖值 > 启动配置。** 这是整件事的目的——UI 上改过的值必须活过下次升级。
代价是「改了启动参数却不生效」，所以启动时会逐字段打日志说明：

```
Runtime config from database: lightx2v_model_latency_seconds = {...}
(startup configuration said {...};
 delete from runtime_configs where key='lightx2v_model_latency_seconds' to go back to it)
```

**两个已知限制**：
① 多 server 分布式部署下，一台写库不会实时同步到另一台的内存，要等重启；
② 读表失败不致命——server 会退回启动配置继续启动，而不是拒绝启动。

落库上线后，`/etc/gpustack/config.yaml` 仍然建议保留：它是「初始配置 / 灾难恢复基线」，
库里没有行的字段仍由它决定。

页面上另有五个按类别阈值（图片 25 / 视频 150 / 语音 60 / 音乐 90 / 音频生成 90）。
15 个对外模型**全部有按模型 override**，所以这五个当前基本不生效，

### 4.7 新模型上线的红线

**新模型必须同时补两张表的行**。不补会落到代码里的按类别默认 latency
（`videos.py:480` 起：image 20 / video 90 / audio 20 / music 30 / audiogen 30），
而实测视频是 127~253 秒——默认值低一个量级，会让队列堆得远比预期深，
背压形同虚设。

### 4.8 背压链路全貌

同步图片链路上是**三道闸门 + 两处真队列**，调准入只动闸门 2：

| | 位置 | 满了怎样 |
|---|---|---|
| 闸门 1 | new-api `imageBlockingSem`（32 并发） | 立即 429，**不排队** |
| 闸门 2 | gpustack 准入 `_check_admission` | 429（本节两张表） |
| 闸门 3 | gpustack→引擎提交，实例内 FIFO 满 | 503 `All instances busy` |
| 队列 1 | gpustack `VideoGenerationTask` 表里 QUEUED 的任务 | new-api 的 `maxQueuedWait=25s` 管的是这里的**等待时长** |
| 队列 2 | 引擎进程内 FIFO（`max_queue_size`，启动设 10） | |

new-api 侧**没有队列**：`maxQueuedWait` 是「容忍 gpustack 侧任务停留在 QUEUED 多久」，
`imageBlockingSem` 是并发闸门（`select` 带 `default`，拿不到令牌立刻 429）。

配置生效前后对照（`z-image`，4 实例）：
配置前 latency 吃默认 20 → 队列深 12 时 `floor(12/4)×20 = 60 > 25` 触发 429（实测报文坐实）；
配置后 latency = 7 → 同样深度 `3×7 = 21 ≤ 25` 放行，28 并发实测 0 次 429。

## 5. 已知问题

### 5.1 ✅ `ltx2.5-hd` 的 2K 档已可用，但余量很薄

**复测结论（2026-09-02）**：`2496x1408 / 15 秒 / 361 帧` 现已稳定出片。
我复测 1 次（端到端 269s、引擎 264s，产物 2496×1408 / 361 帧 / 15.04s / 18.4 MB、带音轨、画面正确）；
`/v2/video-tasks` 里另有同规格任务 8 条，**全部 `done`**，引擎耗时 240~316s。
1080P 两档同步复核通过：5 秒 55s、15 秒 131s。

**但「为什么好了」与直觉不符，值得记一笔**：

- **引擎镜像一字未变** —— 仍是 `sha256:bb30c0e8…`、revision `ffd46bfab21`、
  构建时间 `2026-09-01T12:17:58Z`，与崩溃那次完全相同；
- pipeline 类仍是 `LTX2DistilledTwoStagePipeline`，`--ulysses-degree 4`、
  `--vae-patch-parallel-size 4`、`--quantization int8 --enable-cpu-offload` 都没动；
- **启动参数也没变**：`--diffusion-warmup-shapes` 一直是三个形状
  `1920x1088x121 1920x1088x249 2496x1408x121`（含 2K）；
- **rank0 峰值几乎没变**：本次实测五台的 GPU0 峰值是 40075 / 40191 / 40355 / 40413 / 40433 MiB
  （满卡 40960），而崩溃那次崩前读数是 **40335 MiB** —— 数量级和具体数字都一样。
  也就是说**不是靠腾出显存解决的，是在同一个显存水位上活下来了**。

> **更正（2026-09-02 晚）**：本节早前写过一条推测，说「唯一的部署差异是 warmup shape
> 从三个减到一个，因此改变了 CUDA 缓存分配器的块布局」。**那条推测的前提是错的** ——
> 它来自一次被截断的 grep（`grep -A1` 在遇到下一个 `-` 开头的参数时就停了，只看到第一个
> 形状）。取完整参数后确认三个形状从头到尾都在。前提不成立，推测一并作废。

**所以「2K 为什么从必崩变成 9/9 通过」目前没有确认的解释**：镜像、pipeline 类、并行度、
启动参数全都没变，rank0 的显存水位也没变。在找到真因之前，只能按「余量约 500~800 MiB
的脆弱状态」对待——任何再多占几百 MB 的改动都可能让它复发（开更长时长、换别的 2K 宽高比、
引擎侧任何增加解码期驻留的改动）。
建议：① 改这些参数前先在单实例上复测 2K/15s；② 保留下面这张帧数表作为回归基线。

| duration | 帧数 | W×H×F | 历史 | 2026-09-02 复测 |
|---|---:|---:|---|---|
| 10s | 249 | 0.875e9 | ✅ | — |
| 13s | 313 | 1.100e9 | ❌ 崩 | 未复测 |
| **15s** | **361** | **1.269e9** | ❌ 崩（连环打死 4 实例） | ✅ **9/9 通过** |

15 秒既然通过，13 秒（体积更小）按理也通过，但没实测。

网关侧 `ltx25MaxPixelFrames = 1.30e9` 维持不变即可——它现在与实测边界一致。

### 5.2 `id4` 只认结构化 JSON 提示词

纯文本必被安全过滤拦成灰底占位图（官方 `prompting.md` 明写的已知行为），
而任务状态仍是 `completed`、照常计费。网关层的「自由文本 → 官方 schema」

### 5.3 每实例**首单**要付一次性 Triton JIT 编译
