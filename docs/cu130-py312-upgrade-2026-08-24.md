> 一句话:**lightx2v / acestep 的 cu130 + py3.12 镜像已构建、推 ACR、A100 真机验证通过(`-test` tag),
> 但尚未 retag 到生产;集群 workers/instances 仍是空的,27 个模型 replicas 全 0,50 台宿主机仍关着。**
>

最初诉求是"把 0001-0050 宿主机都换成 51 这台的配置(驱动 580 / CUDA 13),担心现有 cu128 镜像跑不了"。

## 1. 推翻的既有假设(最重要的部分)

这一轮最大的价值不是镜像,而是证伪了几条一直被当作前提的判断。

### 1.1 "cu130 需驱动 ≥580,570 机器跑不了" —— **错的**

出处:`vllm-omni/docs/MiniMax-Music3-接入调研与路线选型报告.md` §5.1,据此立了"升驱动"的项。**该结论从未实测。**

实测(2026-08-24):

| 组合 | 结果 |
|---|---|
| cu130 镜像 → 0050(驱动 570.86.10) | ✅ `torch 2.11.0+cu130`、`cuda avail True`、bf16 matmul 通过 |
| cu128 镜像 → 0051(驱动 580.65.06) | ✅ 4 卡可见、bf16 matmul 通过 |

原因:镜像自带 `cuda-compat-13-0`(CUDA Forward Compatibility),A100 属数据中心卡,官方支持。

旁证:**vllm-omni 从 v0.25.0 起一直是 cu130**,而集群驱动一直是 570 —— H3、HunyuanImage3(bitsandbytes NF4)、
Qwen3-TTS、VoxCPM2、MOSS-TTS 全套实验都是这么跑出来的。查 `hunyuan-image-3` 启动日志确认**没有**
`backend cuda: disabled`(那是 Sogni 记录的 int8 kernel 退化特征,4× 罚单)。

> **结论:驱动升级与镜像 CUDA 版本可以解耦,不必绑定。**
> **红线:任何 cu130 镜像出包必须校验 `dpkg -l | grep cuda-compat`。**漏了这个包,会在 570 机器上
> 全部起不来、而在 580 机器上一切正常,极难排查。(官方 `nvidia/cuda` base 自带,当前无需额外装。)

### 1.2 "旧 cu128 镜像里 decord 可用" —— **错的,是空壳**

```
旧镜像:  import decord 成功,但 __file__ = None,__path__ = ['/opt/LightX2V/decord']
         属性数 0,没有 VideoReader / cpu / bridge,set_bridge 直接 AttributeError
```

`/opt/LightX2V/decord` 是**当初构建机上的残留空目录**(不在 git 里,`.dockerignore` 也没排除),
被 `COPY . /opt/LightX2V` 带进镜像,然后作为 namespace package 劫持了 `import decord`。

危害:它让 `import decord` **成功**,于是所有 `try: import decord / except: fallback` 的分支
**都不走 fallback**,拖到真正调用 `VideoReader` 时才崩。

### 1.3 "SpargeAttn / sgl-kernel 已经在用" —— **错的,一直静默失败**

旧 cu128 Dockerfile 里这几个组件都带 `|| echo skip` 兜底,失败也照常出包:

- **SpargeAttn**:旧镜像 `ModuleNotFoundError: No module named 'spas_sage_attn'` —— 从来没装上过
- **sgl-kernel**:`cd sglang/sgl-kernel` 失败,因为**上游已删除该目录**(改成独立 PyPI 包 `sglang-kernel`),
  所以 `make build` 一次都没执行过 → `dit_quant_scheme=fp8-sgl` 的 FP8 路径一直不可用

本次 Dockerfile 已把静默兜底改为写 `/opt/build-report.txt`,出包后可查。

### 1.4 "A100 能吃 FP8 加速" —— **只能存,不能算**

A100 实测:

```
FP8 存储/转换 : OK   torch.float8_e4m3fn  1 bytes/elem     ← 省显存有效
FP8 _scaled_mm: FAIL "only supported on compute capability >= 9.0 or 8.9"
FP8→bf16 回落 : OK                                          ← 只能反量化后用 bf16 算
```

推论:`SageAttention` 的 **Sage2++**(需 `qk_int8_sv_f8` FP8 kernel)、`sage_attn3`、
`spas_sage_attn3`、`sage_attn2_k_int8_v_fp8` 在 A100 上**永远不可用**,与镜像无关。
日志里 `Warning: Sage2++ NOT enabled`、`sageattention not found`(`sage_attn.py:70` 找的是
`sageattention._qattn_sm90`)都属**正常且无害**的误导性文案。

A100 上实际可用的 attention 后端:**`sage_attn2`** 和 **`spas_sage_attn2`**。

### 1.5 "GPU 节点能上外网" —— **不能**

51 号机实测:`registry-1.docker.io` / `pypi.org` / `github.com` 全 **TIMEOUT**,
只有 `us.download.nvidia.com` 通(Akamai 国内节点,不能当作"有外网"的证据)。

构建拓扑(见 `LightX2V/.github/workflows/build-arm64-docker.yml` 注释):

- **base 层**(全部 CUDA 扩展编译)—— **人工在有外网的 arm64 机器上低频构建**,直连推 ACR。
  CI 干不了:`ubuntu-24.04-arm` runner 有 60 分钟时限,编不完。
- **app 层**(COPY 代码 + `pip install -e --no-deps`)—— GitHub Actions 构建,从 Docker Hub 拉 base。

本次 base 是在**本地 Apple Silicon Mac** 上构建的:架构原生不用 QEMU,CUDA 编译不需要 GPU 在场;
但 **Mac 只能编译不能验收**(无 NVIDIA GPU,`libcuda.so.1` 缺失),运行验收必须回 A100。

## 4. 未完成 / 待办

按建议优先级排:

### 4.1 集群恢复(优先级最高)

1. 开机 0001-0050,观察 worker 是否自动归队(见 §3 的经验)
2. 按恢复清单把 replicas 调回去。**不要一次性全开** —— 50 台同时接入 + 27 个模型抢着拉起 50+ 实例,
   会同时打爆 NFS(权重)和 GPU。按引擎分批、错峰启动。
   既有教训:ARM A100 上任何 4 路 offload 并发会整机死机,单机 ≤2 副本。

### 4.2 驱动升级 0001-0050(570.86.10 → 580.65.06)

**注意:§1.1 已证明这不是上 cu130 的前置条件**,现在做它的理由变成"消除对 `cuda-compat` 的隐性依赖 +
统一基线",优先级可以降低。

- 驱动是 **runfile 装的**(`nvidia-installer` + dkms),不是 apt。**关机重启不会升级驱动**,
  必须在每台上跑 580.65.06 的 runfile。
- 51 号机的 580 是 2026-08-24 11:24 自己用 runfile 升的,流程已跑通一次。
- 内核 5.15.0-187 已被 `apt-mark hold`(4 个 linux 包),这点要保持——驱动模块是 dkms 编译的,内核一升就没了。
- 单机动线:排空实例 → 停 worker 容器 → 确认无进程占 GPU(`fuser /dev/nvidia*`)→ 跑 runfile → reboot → 验证 → 起 worker。
- 调度侧抓手:`gpustack/policies/worker_filters/status_filter.py:21` 只把 `state == READY` 的 worker 当候选,
  所以把 worker 置为 maintenance(state → `MAINTENANCE`)就能挡住新实例落上去。

### 4.3 ~~`-test` → 生产 tag~~ ✅ 已完成(2026-08-25)

### 4.4 sgl-kernel / q8_kernels(建议放弃或降级)

| | 硬件支持 | 实际收益 | 结论 |
|---|---|---|---|
| sgl-kernel (FP8) | ❌ A100 无 FP8 单元(§1.4) | 只省显存,不提速 | **不值得**,除非 40G 显存吃紧 |
| q8_kernels (INT8) | ✅ A100 有 INT8 tensor core | 能提速,但只服务 LTX 模型 | 看有没有 LTX 上线计划 |

已查明的技术细节,供以后继续:

- **sgl-kernel**:官方 PyPI 包已改名 `sglang-kernel`(有 `cp310-abi3-manylinux2014_aarch64` wheel),
  但**在 A100 上装不上**:它找 `sgl_kernel/sm100/common_ops.abi3.so`(sm100 = Blackwell),
  且报 `undefined symbol: torch::Library::_def`(torch ABI 不匹配)。
  ARM64+NVIDIA 的主流组合是 GH200/GB200,官方 aarch64 wheel 只编 sm90/sm100,
  **ARM CPU + A100 PCIe 这个组合落在覆盖范围之外**。要用只能源码编译并指定 `sm_80`。
  **源码位置(2026-08-25 查明)**:已从 `sglang/sgl-kernel` 移走,现在是
  `sglang/python/sglang/kernels/aot`(PyPI 的 Homepage 指向该路径)。
  旧 Dockerfile 里 `cd sglang/sgl-kernel` 就是因此失败的。

  **源码编译尝试结论(2026-08-25,已放弃)**:

  官方 aarch64 wheel 不含 sm_80 的根因找到了 —— `CMakeLists.txt`:
  ```cmake
  if (aarch64)
      set(DEFAULT_ENABLE_BELOW_SM90 OFF)   # 上游假设 aarch64 = GH200/GB200
      message(STATUS "For aarch64, disable gencode below SM90 by default")
  option(ENABLE_BELOW_SM90 ... ${DEFAULT_ENABLE_BELOW_SM90})
  if (ENABLE_BELOW_SM90)
      "-gencode=arch=compute_80,code=sm_80"    # sm_80 在这个开关里
  ```
  即**不是不能编,是 ARM 上默认没编**。加 `-DENABLE_BELOW_SM90=ON` 后,
  nvcc 命令行确认出现了 `-gencode=arch=compute_80,code=sm_80`,开关有效。

  但编译仍失败于两个 **sm90/sm100 专属**源文件:
  `csrc/expert_specialization/es_fp8_blockwise.cu` 与 `es_sm100_mxfp8_blockscaled.cu`,
  它们属于 `common_ops_sm90_build` target 且**被无条件编入**;
  传 `-DSGL_KERNEL_ENABLE_SM90A=OFF -DSGL_KERNEL_ENABLE_SM100A=OFF`
  和 `-DCMAKE_CUDA_ARCHITECTURES=80` 都拦不住(实际 gencode 里仍塞了
  sm_90/100f/120a/110a/121a 一整串)。

  要继续就得改 CMakeLists 把这批源文件排除出 target = **维护一个 fork**,
  上游每次更新都要重新 patch。结合 A100 无 FP8 硬件(收益只有省显存)
  且旧 cu128 镜像同样没有此能力(放弃不算退步),**判定不值得,已停止**。
- **q8_kernels**:内置 `third_party/cutlass` 锁在 commit `b0e09d7`(cutlass 3.6.0, 2024-11-18)。
  编译报 `identifier "PFN_cuTensorMapEncodeTiled" is undefined`,失败文件
  `fp8_matmul_bias.cu` / `q8_matmul_bias.cu`。
  根因:**CUDA 13 移除了不带版本后缀的 `PFN_xxx` 别名**,而 cutlass 至今(v4.7.0 同样代码)
  仍按老写法 `CUTLASS_CUDA_DRIVER_WRAPPER_DECL(cuTensorMapEncodeTiled, 12000)` 声明。
  **所以升级 cutlass 解决不了**。
  已尝试注释掉那两行 TMA 声明(TMA 是 Hopper 特性,sm_80 用不到)→ **编译仍失败**,

## 6. 踩过的坑(按出现顺序)

| 坑 | 现象 | 解 |
|---|---|---|
| Docker Desktop 内存 | 直接改 `settings-store.json` 的 `MemoryMiB` → Docker 起不来(daemon 500) | 必须用 GUI:Settings → Resources → Memory → Apply & Restart。同样的值 GUI 就成功 |
| base 镜像架构 | `nvidia/cuda:13.0.3-cudnn-devel-**ubuntu24.04**` 指定 `--platform linux/arm64` 仍拉到 amd64 → `exec /bin/sh: exec format error` | 换 **ubuntu22.04** 变体正常(而且本来就该对齐宿主机) |
| flash-attn OOM | `MAX_JOBS=16` + 62G 内存 → `ResourceExhausted: cannot allocate memory` | flash-attn 的 nvcc 单进程峰值 **8-10GB**(远高于其他扩展的 2-4GB)。单独用 `FA_MAX_JOBS=4`,不动全局 |
| ACR 推送 | 所有层推完,写 manifest 时 `unknown manifest class for application/vnd.oci.empty.v1+json` | **必须加 `--provenance=false --sbom=false`**。ACR 个人版不认 buildx 的证明清单。(workflow 里早有此注释) |
| Dockerfile 语法 | `RUN python -c "` 后直接换行写 Python → `unknown instruction: import` | RUN 续行每行都要 `\`;或用 BuildKit heredoc `RUN python - <<'PY'` |
| 构建期 import | app stage `import lightx2v` → `RuntimeError: AI device for platform 'cuda' is not available` | **构建期不能 import lightx2v**,其 `__init__` 会硬断言 CUDA 设备存在。原 Dockerfile 从不这么做 |
| zsh 变量 | `docker tag $ACR:arm64-...` → tag 变成 `.../lightx2vrm64-...` | zsh 把 `$ACR:a` 当作修饰符 `${ACR:a}`(绝对路径展开)。**必须写 `${ACR}:`** |
| 看不到构建进度 | `docker build ... \| tail -N` 会缓冲到结束才输出 | 重定向到文件 `> /tmp/build.log 2>&1`,随时可 tail。ssh 命令套 `\| tail` 同理 |
