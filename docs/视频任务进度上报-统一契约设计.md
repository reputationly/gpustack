## 0. 决策摘要(本次拍板)

| 项 | 决策 |
|---|---|
| 契约位置 | **引擎状态接口(`GET /v1/tasks/{id}/status`)扩展可选字段**,不新增端点、不引入推送 |
| 归一化位置 | **在 GPUStack 门面**做阶段权重折算与兜底,引擎只报"我在哪个阶段、这个阶段走了多少" |
| 阶段词表 | 受控 5 词:`prepare` / `encode` / `denoise` / `decode` / `save`(与现有 profiler stage 命名对齐) |
| 引擎不上报时 | **时间估算兜底**(elapsed / 预估时长),复用现成的 `lightx2v_model_latency_seconds` 标定表;封顶 95,永不倒退 |
| 首批适配引擎 | **vLLM-Omni(MiniMax-H3,含 prepare/encode 准备阶段)** + **LightX2V(Wan2.2 系,复用其现成 progress_callback)** |
| 引擎内传输 | vLLM-Omni 复用既有 `result_mq` 异步输出通道(新增一种消息 kind),**不新增进程/端口/ZMQ** |
| 持久化 | `video_generation_tasks` 新增 `progress` / `phase` / `run_started_at` 三列(进度可在管理端可见、单调判定有依据) |
| new-api | **零改动**——消费端(`adaptor.go` 的 `statusResponse.Progress`)早已写好,只是一直收不到字段 |
| 向后兼容 | 老引擎不返回新字段 → 门面走兜底;老门面不返回新字段 → new-api 退回固定 30%。**任一侧单独升级都不报错** |

## 1. 背景:进度为什么卡在 30%

new-api 体验区里,自建渠道(GPUStackPlus)的视频任务一旦进入 `running`,进度条就**停在 30% 直到出片**。一个 768p/15s 的 H3 任务要跑数分钟,用户全程看不到任何推进,分不清"在跑"和"卡死"。

三层实测事实(代码坐标为准):

| 层 | 现状 | 代码坐标 |
|---|---|---|
| **new-api(消费端)** | **已就绪**。`statusResponse` 声明了 `progress` / `phase`;`scaleProgress` 把门面的全局 0-100 折进 `[30,95]`(100% 在 new-api 里是终态语义,10%/20% 已被 submitted/queued 占用);`ParseTaskResult` 只在 `progress > 0` 时覆盖固定档位;轮询层用 `taskResult.Progress` 覆写 | `relay/channel/task/gpustackplus/adaptor.go:126-159, 1465-1471`;`service/task_polling.go:503` |
| **GPUStack 门面(中枢)** | **完全缺失**。任务表无进度列;`_public()` 不返回;`fetch_engine_status_updates()` 只把引擎 `status` 映射成 state,拿到的其余字段全丢 | `schemas/video_generation_task.py`;`routes/videos.py:1567-1619, 1716-1727` |
| **引擎(数据源)** | **没有上报**。vLLM-Omni 的 `AudioTaskResponse` 只有 status/时间/错误;LightX2V 的 runner **有** `set_progress_callback` 基建但**全仓无人调用**,`get_task_status()` 也不输出 | `vllm_omni/entrypoints/openai/protocol/audio_tasks.py:158`;`lightx2v/models/runners/default_runner.py:220,247`;`lightx2v/server/task_manager.py:165` |

结论:**契约的两端都在,中间两段没接**。new-api 的注释里写的"门面已按阶段权重表折算好的全局进度"描述的是一个**当时设想、从未落地**的设计——本文就是把它补齐。

## 2. 目标与非目标

**目标**

1. H3(vLLM-Omni)能报出真实进度,且**准备阶段可见**——参考视频抽帧、文本/VAE 编码在 ref2va 上占用可观时间,不能等到进采样循环才开始动。
2. 在门面沉淀**引擎无关的抽象**:新引擎接入只需按契约吐字段,门面零改代码。
3. 存量未适配的引擎(Bernini / ACE-Step / IndexTTS)**立刻**摆脱卡 30%(兜底估算)。

**非目标(本轮不做)**

- 不做推送(webhook / SSE):门面已是 poll-on-GET 模型(§6.0 的"薄门面"决策),new-api 15s 轮询,进度精度到秒级没有意义。
- 不做排队位次展示(queued 阶段仍是固定档位)。
- 不做前端进度条改造:new-api 现有进度条直接受益。
- 不改 `_ENGINE_STATE_MAP` 的状态词表——进度是**旁路信息**,状态机不变。

## 3. 统一契约

### 3.1 数据流

```
┌──────────────── 引擎进程 ─────────────────┐
│ pipeline (worker)  ──进度事件──▶ 任务状态表 │   GET /v1/tasks/{id}/status
└───────────────────────────────────────────┘            │ progress/phase/phase_progress/step
                                                         ▼
                                       ┌──── GPUStack 门面 ────┐
                                       │ normalize_progress()  │  阶段权重折算 + 单调 + 兜底
                                       │ video_generation_tasks│  progress / phase / run_started_at
                                       └───────────────────────┘
                                                         │ GET /v1/videos/{id} → {"progress":42.5,"phase":"denoise"}
                                                         ▼
                                       ┌────── new-api ────────┐
                                       │ scaleProgress → "58%" │  [30,95] 区间,终态 100%
                                       └───────────────────────┘
```

### 3.2 引擎 → 门面(状态接口扩展)

全部**可选**字段,老引擎不返回即视为未适配:

| 字段 | 类型 | 语义 |
|---|---|---|
| `progress` | float 0-100 | 引擎已自行折算好的**全局**进度。**最高优先级**——引擎最清楚自己的阶段耗时分布,报了就直接采信 |
| `phase` | string | 阶段名,取自 §3.3 受控词表。越界值按未知处理(只记日志,不参与折算) |
| `phase_progress` | float 0-100 | **阶段内**百分比 |
| `step` / `total_steps` | int | 采样步数计数。等价于 `phase="denoise"` + `phase_progress=step/total_steps*100` 的语法糖,给"只想改一行"的引擎用 |

**引擎侧的最小适配** = 在采样循环里报 `phase="denoise", step, total_steps`。有余力再补 prepare/encode/decode/save 四段。

### 3.3 受控阶段词表

与 `vllm_omni/diffusion/profiler/diffusion_pipeline_profiler.py` 的 stage 命名保持同一套语汇,便于把耗时 profile 和进度对照看:

| phase | 含义 | 典型内容 |
|---|---|---|
| `prepare` | 输入准备 | 参考视频抽帧/对齐、图片缩放、音频重采样 |
| `encode` | 条件编码 | 文本编码器、VAE encode、音频条件编码 |
| `denoise` | 扩散采样主循环 | 逐步去噪(占大头) |
| `decode` | 结果解码 | VAE decode |
| `save` | 后处理与落盘 | 后处理、mp4 封装、写 NFS |

### 3.4 门面 → new-api

`_public()` 增加两个字段,其余不变:

```json
{
  "task_id": "...", "status": "running", "model": "...", "task_type": "ref2va",
  "nfs_path": null, "error": null, "error_type": null,
  "progress": 42.5,
  "phase": "denoise"
}
```

`status=done` 时 `progress` 恒为 100。new-api 侧无需任何改动。

这个 100 **在库里落盘**,不只在 `_public()` 里现算:`_public()` 不是唯一读者,管理面 `GET /v1/video-tasks` 的 `VideoTaskPublic` 直接继承 `VideoTaskBase` 原样序列化这几列,不经掩盖。若终态只掩盖不落盘,任务面板会显示"done · 92.7%"。同理迁移必须回填历史行(`UPDATE ... SET progress = 100 WHERE state = 'DONE'`),否则存量任务全是"done · 0%"。

`failed` / `canceled` **有意保留跑到的进度和阶段**——"死在 82% 的 denoise"是排查线索,而客户端对终态本来就按完成处理。

## 4. 门面归一化模型

新增纯逻辑模块 `gpustack/server/video_progress.py`(不 import routes,避免与 `videos.py` 循环依赖;kind、预估时长由调用方传入)。

### 4.1 阶段权重表

按 engine kind(`_engine_kind()` 已有的 video/image/audio/music/audiogen 分类)各一套,视频默认:

| phase | 权重 |
|---|---|
| prepare | 8 |
| encode | 12 |
| denoise | 60 |
| decode | 15 |
| save | 5 |

依据:H3 768p/15s 的实测形态——采样占大头,但 VAE decode 在长视频上不可忽略(单次解码可达分钟级、显存峰值 4GiB+ 拷贝,见 `pipeline_minimax_h3.py` forward 尾部注释),给到 15;ref2va 的参考视频抽帧走 CPU/ffmpeg,给 prepare 留 8。权重表是**门面侧常量**,后续按线上标定微调,不需要引擎配合。

全局进度 = 前序阶段权重之和 + 当前阶段权重 × `phase_progress`/100。

### 4.2 归一化算法

```
normalize_progress(payload, *, kind, prior, elapsed, expected_seconds) -> (progress, phase, source)

1. payload.progress 有效        → value = clamp(payload.progress), source="engine"
2. phase + phase_progress 有效  → value = 权重表折算,            source="engine"
3. step/total_steps 有效        → 按 denoise 阶段折算,           source="engine"
4. 否则                         → value = 100*elapsed/expected,  source="estimate"
5. 运行中封顶:engine 源封顶 99,estimate 源封顶 95(估算永远不许逼近完成)
6. 单调(**尝试内**):return max(value, prior)
```

**为什么 estimate 封得比 engine 更低**:估算失准时宁可"慢"不可"快"——进度条冲到 99% 再干等几分钟,比停在 95% 更像卡死。

**为什么尝试内单调**:同一次运行里进度**源会抖**——引擎这一跳报了百分比、下一跳只报 phase 或什么都不报,就会掉回更低的估算值;运行中途进度条倒退在 UI 上是明确的故障信号。

**为什么跨尝试必须清零**:重派是**新的一次运行**,引擎侧计数从零开始。若把上一次的高水位带过去,一个跑到估算封顶(95)才死掉的尝试会把它的重试**整轮钉死在 95%**——这正是封顶机制本身要避免的"看着像卡死"。所以单调性只在一次尝试内成立,尝试结束时由调用方清零(`ATTEMPT_RESET`),见 §4.4。

**为什么不锚在派发时刻**:`run_started_at` 取的是**首次观测到 RUNNING**,不是派发。引擎有自己的内部队列,任务可能在引擎侧 `pending` 好几分钟才真正开跑,锚在派发会系统性**高估**——按上一条,高估才是更贵的失败。代价是锚点最多迟一个轮询周期(new-api 15s),对分钟级任务是可接受的常数偏移,且随运行推进相对误差收敛。

### 4.3 时间估算兜底

- `expected_seconds` 复用现成的准入标定 `_model_latency(cfg, model_name, task_type)`(`routes/videos.py:763`)——那张表本来就是"这个模型跑一单大概多久"的线上标定,零新增配置。
- `elapsed` 从 **`run_started_at`** 起算,不能用 `updated_at`:每次 poll 的 `task.update()` 都会刷新 `updated_at`,拿它算 elapsed 会永远接近 0。`run_started_at` 在任务首次进入 RUNNING 时写一次。
- 也不能用 `created_at`:那里面含排队等待,长队列下会把进度冲高。

### 4.4 持久化与尝试边界

`video_generation_tasks` 新增三列(三库兼容,`UTCDateTime`):

| 列 | 类型 | 用途 |
|---|---|---|
| `progress` | float,默认 0 | 单调判定的 `prior`;管理端/排查可见 |
| `phase` | varchar,可空 | 排查用;未来 UI 可展示"正在解码" |
| `run_started_at` | UTCDateTime,可空 | 估算基准 + 顺带得到真实运行时长统计 |

**不做写库节流**:`fetch_engine_status_updates()` 返回的 updates 恒含 `state`,也就是说非终态任务**每跳轮询本来就要写这一行**,进度只是搭车多写两列——为省这两列去做"变化 < 1 点不写"的判断,省不到一次 DB 写,却要额外处理"响应必须用新鲜值、库里可以是旧值"的不一致。

**尝试边界清零**(`ATTEMPT_RESET = {progress: 0, phase: None, run_started_at: None}`,§4.2):三个结束尝试的路径都要 splat 进 update——sweeper 的死亡重排(`video_task_sweeper._requeue`)、`fetch_engine_status_updates` 的 404 丢任务重排、`redispatch_task` 的重派。最后一处看似冗余(重排时已清过),保留是为了让"从未被重排、直接从 QUEUED 派出去"的行也自洽。

> 常量而非三处字面量:这个 dict 是 splat 进 `task.update()` 的,写错 key 不会报错、只会静默漏清一列。测试直接断言 key 集合与行字段对得上。

### 4.5 一处必须修的既有逻辑

`fetch_engine_status_updates()` 现在遇到 `_ENGINE_STATE_MAP` 查不到的状态就 `return None`(`videos.py:1610`)。引擎状态没变(一直 `processing`)时它返回的是有效映射,不受影响;但为了让"状态不变、只有进度变"的情形也能折进度,该函数的返回结构要从"状态映射"扩成"状态映射 + 进度",且进度分支不受状态分支早退影响。

sweeper(`server/video_task_sweeper.py`)复用同一个函数,自动继承,无需改动。

## 5. 引擎适配

### 5.1 vLLM-Omni(MiniMax-H3)

难点是**进程边界**:pipeline 的 `forward()` 跑在 mp executor 拉起的 worker 子进程里,而状态接口在 API server 进程。

**已核实的可用通道**:worker 与 executor 之间已有一条异步输出通道——worker 侧 `result_mq.enqueue(AsyncDiffusionOutput(...))`,executor 侧 `_result_pump` 线程是该队列的唯一读者,按 `kind` 分发(`RPC_RESULT` / `COMPUTE_DONE` / `OUTPUT_READY`)。进度只需**再加一种 kind**,复用整条链路,不新增进程、端口或 ZMQ。

设计要点:

1. **`vllm_omni/diffusion/progress.py`(新)**——仿 `forward_context.py` 的模块级上下文写法:
   - `set_progress_sink(fn)`:worker 启动时注册(仅 rank 0;其余 rank 的 `result_mq is None`,天然静默,与 `_return_result` 同款约定)。
   - `progress_scope(request_id)`:model runner 在调 pipeline forward 处开启(与 `set_forward_context` 同层)。
   - `report_phase(phase, completed=None, total=None)`:pipeline 内部调用;**无 sink 时 no-op**,所以离线推理/单测/直接调 pipeline 的路径完全不受影响。
   - **节流内置在这里**:≥0.5s 或 ≥1 个百分点才真正发一条;任何异常吞掉。`result_mq` 是定长共享内存环形队列,**进度绝不允许阻塞或拖垮推理主路径**。
2. **executor**:`_result_pump` 增加 PROGRESS 分支,写 `self._progress[request_id]`;请求终结时清理。事件挂在现有 `AsyncDiffusionOutput.result`(类型是 `Any`),不加字段。
3. **透出**:`diffusion_engine` → `inline_stage_diffusion_client` → `AsyncOmni` 逐层 `get_progress(request_id)`。
   - H3 走 **inline** 路径(`stage_runtime.py:659`:`use_inline = num_stages==1 and num_replicas==1`),引擎与 API server 同进程,直接读。
   - out-of-proc 的 `StageDiffusionClient`(多阶段/多副本)本轮返回 `None`,退化为门面时间估算。**这是明确的作用域边界,不是遗漏。**
4. **H3 打点**:`prepare`(参考视频抽帧前)、`encode`(文本/视觉/音频条件编码段)、`denoise`(`denoise_loop.py` 的采样循环内,带 step/total)、`decode`(VAE 解码段);`save` 由 API server 进程在写 mp4 时自己标(不走 IPC)。
5. **状态接口**:`AudioTaskResponse` 增加 `phase` / `phase_progress`(不报全局 `progress`——阶段权重归门面);`GET /v1/tasks/{id}/status` 对 PROCESSING 任务**当场向引擎取**实时进度,而不是把它存进任务行:pipeline 在 worker 进程里异步推送,轮询时刻拉到的才是最新值。`save` 阶段例外,那段发生在 server 进程,直接写任务行。
   - **task_id 就是引擎 request_id**——`_run_video_task_job` 把 `task_id` 当 `reference_id` 传给 `generate_video_bytes`,一路传成 `engine_client.generate(request_id=...)`,映射天然存在,无需额外登记表。

### 5.2 LightX2V

基建已经躺在仓里,只是没接线:

- `models/runners/default_runner.py:220,247` 有 `set_progress_callback` 和 `progress_callback((current_step/total_all_steps)*100, 100)`,但全仓无调用点。
- 接法:`server/services/inference/worker.py` 在 `run_pipeline` 前挂回调 → 写 `TaskManager` 的 `progress`/`phase`(`phase="denoise"`),`get_task_status()` 输出。
- 线程安全:推理跑在 `server/api/server.py` 的独立 `processing_thread`,`TaskManager` 自带 RLock;仅 rank 0 生效(`submit_task_async` 已有 rank 判断)。

Wan2.2 / SeedVR2 等走 LightX2V 的模型由此直接受益。

### 5.3 其余引擎

Bernini / ACE-Step / IndexTTS 本轮不改,走门面时间估算兜底。想接入时按 §3.2 吐字段即可,门面无需改代码。

## 8. 风险与取舍

| 风险 | 处置 |
|---|---|
| 进度事件拖慢推理 | 节流 + 异常吞掉 + 仅 rank 0;`result_mq` 满时丢弃而非阻塞 |
| 估算失准误导用户 | 估算档封顶 95;`source` 先只进日志,若线上反馈"假进度"再往上透字段由前端弱化展示 |
| 重派导致进度倒退 | 门面强制单调(§4.2) |
| 迁移链断言漏改 | 已在 §6 单列 ⚠️;出包前 `alembic heads` 自检 |
| 多副本/多阶段部署拿不到真实进度 | 明确降级到估算,不做隐式承诺;后续如需支持,在 `StageDiffusionClient` 的 ZMQ 响应流上补一种消息类型即可(通道形状与 result_mq 一致) |
