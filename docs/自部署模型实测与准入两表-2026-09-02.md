# 自部署模型实测与准入两表建议值（2026-09-02）

> 目的：给 GPUStack「按模型延迟(秒)」`lightx2v_model_latency_seconds` 与
> 「按模型最大排队等待(秒)」`lightx2v_model_queue_wait_seconds` 填出有实测依据的值。
>
> 测量方式：走生产网关 `https://maas.ovaijisuan.com` 打真实请求 + 从 GPUStack
> `GET /v2/video-tasks` 取同批任务的 `run_started_at → updated_at` 交叉验证。
> 产物逐个下载、`ffprobe` 验参、图像/视频抽帧目视确认。

## 0. 一句话结论

- **两表当前都是 `null`**（`GET /v2/config` 实读），全集群吃默认值 `image 20/25 · video 90/150 · audio 20/60 · music 30/90`。
- 默认值与实测偏差最大处达 **3 倍**（z-image 实测 6.1s，默认按 20s 估），直接后果是 **429 提前约 3 倍触发**。
- 本轮实测 **18 个**自部署模型（16 个媒体模型 + `qwen3-embedding-8b` / `qwen3-reranker-8b`）：
  **18 个全部可用**（`id4` 需按官方结构化 JSON 格式写提示词，见 §3.1——早前判定它
  「完全损坏」是我用错格式导致的误判，已更正）。另有 **2 类玩法不可用**
  （`ltx2.5` / `ltx2.5-hd` 的首尾帧、`ltx2.5-hd` 的 2K 档）。
- ⚠️ 别把 18 和 19 搞混：GPUStack 上**有实例**的模型是 19 个，其中
  `minimax-h3-base-fl2va` / `fast-fl2va` / `fast-ref2va` 三个 maas 未暴露、本轮**没测**（见 §3.8）。

### 1.1 视频档位的载荷依赖

`ltx2.5` / `ltx2.5-hd` 的耗时**几乎与时长线性**（5s→15s 差 4.6~5.4 倍），
所以延迟表填哪个数是个取舍：

- 填 **15s 档**（148 / 230）：短任务被高估 4.6 倍，429 提前触发；
- 填 **5s 档**（32 / 43）：长任务被低估，队列真实等待远超估算，用户干等。

**建议填 15s 档**：视频链路是异步轮询、容忍度高，宁可早拒也不让用户挂着；
且 15s 是这两个模型对外承诺的时长上限，产品主推成片长度也是它。

⚠️ **`minimax-h3-*` 有同样的问题但表里没体现**：它的时长范围是 4~15 秒（`relay/channel/task/gpustackplus/minimax_h3.go:45-46`），本轮只实测了 5 秒档（fl2va 158s / ref2va 253s）。15 秒档没测，按线性外推约 470s / 760s。若产品面向 H3 也开放长时长，这两个值要相应上调，否则同样会低估。

## 2. 建议填入的两张表

### 2.1 按模型延迟(秒) `lightx2v_model_latency_seconds`

取实测引擎耗时中位数向上取整。**同一模型多个玩法取最慢的那个**——准入在提交时
还不知道这单要跑多久，按最慢档保护。

**行序不用管**（早前版本的本文档说「必须长键在前」，说过头了，已更正）。
`05cac5fb fix(videos): 准入查表改为精确优先` 之后，`_lookup_by_model`
（`routes/videos.py:753`）先做一趟精确匹配，命中就返回；线上镜像（2026-08-29 构建）
已包含该提交。

保留的子串回退只服务一个调用方——进度轮询器（`videos.py:1704`），
它手上只有提交时持久化的 `task.model_name`（可能是路由名 / `owner/name` / 上游别名）。
准入 `_check_admission`（`videos.py:1059`）传的是库里的权威 `model.name`，走的是精确那一趟。

在本部署下连回退都走不到：new-api 下发的 `body["model"]` 是渠道映射后的上游名，
我们没做模型重命名，所以 `task.model_name` 与 `model.name` 逐字一致（已核过任务数据）。
即便哪天真的落到回退，影响也只是进度条百分比的估算基数
（`expected_seconds` 喂给 `normalize_progress`），**不影响 429、不影响出片**。

### 2.2 按模型最大排队等待(秒) `lightx2v_model_queue_wait_seconds`

判据 `est_wait = floor(非终态任务数 / 运行实例数) × latency`，超过即 429。
设 `queue_wait = K × latency` 等价于「每实例最多积压 K 个任务」。分链路取 K：

**同步图片链路**（`/v1/images/generations` 不带 async）：客户端阻塞在等。
必须与 new-api 侧的 QUEUED 容忍**对齐**——两道闸门任一收紧都会先失败
（`relay/channel/gpustackplus/adaptor.go:61` `maxQueuedWait = 25s`；
慢模型清单 `GPUSTACKPLUS_SLOW_IMAGE_MODELS` 命中者 240s）。

**异步任务链路**（`/v1/videos`）：客户端自己轮询，无硬超时，K 是纯产品决策
（用户愿意等多久）。实例多的取小 K（绝对深度已经够），实例少的取大 K。


`routes/config.py` 的 `set_config` 只做 `setattr`，**不落盘**——`gpustack-server`

### 2.4 背压公式已实测验证

对 `z-image` 并发打 40 单（4 实例、默认 latency=20 / ceiling=25）：

```
28×200  9×429  3×503
429 报文：系统繁忙,请稍后再试 (estimated queue wait 60s > 25s)
          系统繁忙,请稍后再试 (estimated queue wait 140s > 25s)
```

`floor(12/4)×20 = 60`、`floor(28/4)×20 = 140` —— 与公式精确吻合。
另有第二道闸门：503 `All instances busy`（实例内 FIFO `max_queue_size` 满），
与准入是独立的两层，**调准入不影响它**。

## 3. 实测发现的问题

### 3.1 🟠 `id4` 需要结构化 JSON 提示词——早前判定「完全损坏」是我错了

**更正**：本文档早前写的「`id4` 完全损坏，4 个提示词全部返回 safety filter 占位图」
**结论错误**。模型本身完全正常，是**我用错了提示词格式**。

Ideogram 4 官方 `docs/prompting.md` 明确写着：

> Ideogram 4 is trained exclusively on **structured JSON captions**.
> Passing in plain-text prompts directly to the model **will not work and will likely
> trigger a safety warning**. False positive rates for safety is high for non-json prompts.

我那 4 个提示词全是纯文本，命中的正是这条已知行为。补做的受控对照（同模型、同尺寸、
同 `task_type`、前后脚发出）：

| `prompt` | 结果 |
|---|---|
| `a single red apple on a plain white table, studio lighting, photorealistic`（纯文本） | ❌ 灰底占位图 |
| 同一语义的官方结构化 caption（`high_level_description` + `style_description` + `compositional_deconstruction`） | ✅ 正常出图，与描述逐项吻合 |

另测了 `art_style` 插画分支与 `type:"text"` 图内文字渲染，均正常
（海报上的 `COFFEE FEST` / `MARCH 14-16` 两行文字逐字准确）。

**真正的问题不在模型，在网关层缺一层转换**：
`vllm-omni/docs/Ideogram-4-vLLM-Omni移植与冒烟验证报告-2026-08-27.md` §5.6 / §8 第 1 条
已把「门面层实现『自由文本 → 官方结构化 JSON schema』转换层」列为**最高优先级遗留工作**，
至今未做。所以现网用户按常规习惯发自然语言，100% 拿到占位图。

**仍然成立的次级问题**：被拦截时任务状态是 `completed`、进度 100%，
`service/task_billing.go` 的 `RefundTaskQuota` 只在失败时退款，所以**照常计费**，
客户端无从分辨。这条值得单独修——至少在门面层检测
`Image blocked by safety filter` 这个固定文案并判为失败。

**处置建议**（替代早前的「先摘掉 id4」）：
1. 文档侧已补：`newapidocs` 新增「id4 提示词写法」页，讲清 schema、严格键序、`bbox` 坐标系
   与三个实测示例；`create-t2i` 与总览页都已加显著提示；
2. 网关侧补 magic-prompt 转换层（把自然语言扩写成官方 schema），这是根治；
3. 补「检测占位图文案 → 判失败 → 退款」的兜底。

⚠️ 另据同一份报告 §5.8：模型自带安全对齐**只覆盖 NSFW 类内容，不拦截暴力/血腥**
（6 组图形化暴力测试全部通过）。有合规要求需业务侧另做审查。

### 3.2 ✅ 已解决：`ltx2.5-hd` 的 2K 档（2026-09-02 复测 9/9 通过）

> **状态更新（2026-09-02 晚）**：2K/15s 已稳定，复测 9/9 通过，详见
> [`现网部署现状-2026-09-02.md`](现网部署现状-2026-09-02.md) §5.1。
> 但引擎镜像一字未变、rank0 峰值仍在 40.1~40.4 GB / 40.96 GB（与崩溃时几乎相同），
> 余量只有约 500~800 MiB，**很脆**。本节保留作为根因分析与回归基线。

**根因（2026-09-02 受控复现坐实）：两阶段 pipeline 在 2K 长帧数下，VAE 解码后的
postprocess 把结果 gather 收敛到 rank0，rank0 单张 A100-40G 装不下。**

直接对 0053 的引擎口（绕过门面，避免 re-dispatch 连环打）发 `2496x1408 / 361 帧`，
每 3 秒采样显存与主机内存：

```
08:40:29  GPU0 34797  GPU1-3 33753   去噪中，四卡均摊
08:40:32  GPU0 15215  GPU1-3 14791   pre-VAE 卸载 DiT，各卡释放约 19 GB
08:40:39  GPU0 40335  GPU1-3 15331   ← rank0 独自冲到 40335/40960 MiB（剩 625 MiB）
08:41:12  进程消失
```

- **不是主机 OOM**：主机内存峰值 137 GB / 251 GB，全程剩 110 GB 以上；
  `dmesg` / `kern.log` / `journalctl -k` 在该时刻**零记录**，容器也没设 memory limit。
- **不是超时**：四次崩溃的「卸载 DiT → 死亡」间隔是 216s / 39s / 45s / 121s，毫无规律；
  去噪阶段每次都稳定跑完（约 4 分 11 秒）。
- **不是镜像旧**：`ltx2.5` 与 `ltx2.5-hd` 跑的是同一个镜像
  （`sha256:bb30c0e8…`，revision `ffd46bfab21`，构建于 09-01 20:17），
  已包含 `31067fe1「分块 postprocess + gather 收敛到 rank0，解码包络从 ~1.25e9 抬到 ~1.42e9」`
  （该提交 09-01 20:13 合入 main）。

`DiffusionWorker-**0**` 死亡与「GPU**0** 打满、GPU1-3 闲置」精确对应 ——
死的就是 gather 的收敛点。rank0 分配失败发生在 Python 捕获不到的路径，
所以既没有 `torch.OutOfMemoryError` 也没有 traceback，
`multiproc_executor.py:448` 只能报 `exitcode=None`（它对信号杀会打印 `-9 SIGKILL`，这里不是）。

### 3.2.1 网关的显存包络对两阶段偏松

实测夹逼（同一部署、同一镜像）：

| 尺寸 × 帧数 | W×H×F | 结果 |
|---|---:|---|
| 1920×1088 × 121 | 2.53e8 | ✅ 34~51s |
| 1920×1088 × 361 | 7.54e8 | ✅ 224~235s |
| 1408×2496 × 249（2K 竖） | 8.75e8 | ✅ 269s |
| 2496×1408 × **313** | **1.10e9** | ❌ rank0 死在 35535/40960 MiB |
| 2496×1408 × **361** | **1.269e9** | ❌ rank0 死在 40335/40960 MiB |

**两阶段的真实上限落在 8.75e8 与 1.10e9 之间**，而
`relay/channel/task/gpustackplus/ltx25.go` 的 `ltx25MaxPixelFrames = 1.30e9` 把它们全放行了。

那份包络注释标定的是 `2496×1408×361 = 1.269e9 ✅`，与实测相反。最可能的原因是
**标定跑在单阶段部署上**——注释自己写明参照的是 `dev-gpustack-a100-0017`，而该节点的启动参数是
`--model-class-name LTX2Distilled**OneStage**Pipeline`；2K 只有
`ltx2.5-hd` 在跑，它是 `LTX2Distilled**TwoStage**Pipeline`。
`ltx25MaxOutputSec` 已经按一阶段/两阶段分了两档，`ltx25MaxPixelFrames` 却仍是**两档共用一个常量**——
缺口就在这里。

**处置建议**（按代价从小到大）：
1. 立刻：把 `ltx2.5-hd` 的 2K 档从对外菜单与按秒计费里摘掉（`/api/pricing` 现配 `2K: 0.182/s`，
   属于「卖得出去、跑不出来」），1080p 全档位正常，不受影响；
2. 短期：给 `ltx25MaxPixelFrames` 拆出两阶段专用的低值（≤ 8.75e8 是已验证安全点），
   让越界请求在网关侧 400，而不是进队列打死实例；
3. 中期：两阶段 2K 要么把 postprocess 的 gather 也分块流式落盘（别在 rank0 聚齐整段），
   要么换 80G 卡。

⚠️ 另有一个**放大伤害**的机制与本问题正交：任务打死实例后，
GPUStack 的 sweeper 会把它 re-dispatch 到下一个实例、再打死，轮完 4 个实例才
`dispatch retry cap (5) exceeded`，**单个任务耗时 33 分钟，并让该模型约 25 分钟处于 2/4~3/4 降级产能**（见下方更正 2）：

```
00:34:40 assigned to instance 1014
00:38:44 Requeued (instance 1014 no longer running) → Re-dispatched to 1015
00:42:55 Requeued (instance 1015 no longer running) → Re-dispatched to 1013
00:48:56 Requeued (instance 1013 no longer running) → Re-dispatched to 1016
00:54:12 Requeued (instance 1016 no longer running) → Re-dispatched to 1015
01:07:24 dispatch retry cap (5) exceeded
```

即「能打死实例的请求」会被自动重放到每一个实例上。第 2 条（网关侧提前拒）能堵住这条放大链。

1. 上面这段日志是**第一个** 2K 任务（`486df3c1`，Beijing 00:34–01:07）的轨迹；
   前文 §3.2 那张「卸载 DiT → 死亡」的耗时表来自**第二个** 2K 任务
   （`7e52d95d`，UTC 17:12–17:37）。两个任务各自把四个实例轮了一遍，现象一致，
   但不是同一条时间线，早前把两者并排叙述属表述不清。
2. 早前写的「**让整个模型不可用约 20 分钟**」**不成立**。实测单实例从崩溃到 `/ready` 200
   需约 **410 秒**，而打死间隔约 5.5 分钟，所以是滚动降级而非全断：

### 3.3 🟡 `ltx2.5` / `ltx2.5-hd` 的「关键帧」只支持首帧，不支持首+尾帧

传两张图 → `LTX I2V prompt dictionaries support exactly one image per prompt.`
两个模型都一样。

**这不算标错**：「关键帧」这一格本来就覆盖 `i2v`（只给首帧）/ `l2va`（只给尾帧）/
`flf2v`（首+尾帧）三种玩法，首帧是其中一种，LTX 系支持它。
需要说清的只是「LTX 系拿不到首+尾帧那一档」，文档里按这个口径写。

单图 `i2v` 正常（ltx2.5 31s / ltx2.5-hd 48s），所以「关键帧」这个 tab
在 LTX 系上**只有首帧模式可用**，首+尾帧必须走 `minimax-h3-fl2va`（实测正常，132s）。

### 3.4 🟠 `sensenova-u1.5` 不显式给 `task_type` 会被判成 `t2v`，烧 GPU 产出 1 帧废视频

`{"model":"sensenova-u1.5","prompt":...,"size":"1024x1024"}` 不带
`metadata.task_type` → 网关解析成 `t2v` → 落到 `t2v-sensenova-u1.5/...mp4`，
产物是一个 **0.04 秒（单帧）的 mp4**。而该模型的能力标签只有「文生图/图生图」。
显式带 `metadata.task_type=t2i` 才正常出 PNG。

根因在体验区配置：该模型的 tab 声明里含视频类玩法，导致候选集里有 `t2v`。
建议在体验区管理页把 `sensenova-u1.5` 的 tab 收敛到 text2image / image2image。

### 3.5 🟠 `qwen-image-edit`（31s）已经超过同步链路 25s 的 QUEUED 预算

4 实例满载后，第 5 单必然在 QUEUED 待 ~31s > `maxQueuedWait=25s`，
new-api 直接「系统繁忙」。建议把它加进
`GPUSTACKPLUS_SLOW_IMAGE_MODELS`，并把两侧一起放宽到 ~120s
（gpustack 的 `queue_wait` 同步改成 120）。

### 3.6 🟠 每实例**首单**要付一次性 Triton JIT 编译——「indextts-2.5 慢 5 倍」是我的误判

**更正**：早前写的「`indextts-2.5` 比上一代慢约 5 倍」**结论错误**。
它的热态约 **15 秒**，与 `moss-voicegen`（16s）、下线的 `indextts-2`（16~17s）同级，一点不慢。
我那 4 条样本里有 3 条恰好是各自实例的**首单**，中位数被拉到 87.8s。

**根因（实例 917 首单日志坐实）**：

```
03:12:37 TTS speech request audio_task_a7369798c8f2b48b: model=indextts2_5
03:12:39 WARNING [jit_monitor.py:135] Triton kernel JIT compilation during inference: kernel_unified_attention
03:12:41 INFO    [S2Mel] DiT caches initialized (freqs_cis + causal_mask)
03:14:12 WARNING [jit_monitor.py:135] Triton kernel JIT compilation during inference: SnakeBeta._init_triton
```

两次 Triton JIT 编译相隔 93 秒，就是那 96.3 秒的全部。同实例第二单（03:14:27）15.2s，无 JIT 警告。
用一段**全新参考音色**连发 5 单复现，落点与耗时完全对应：

| 落到的实例 | 916 | 916 | 915 | **917（首单）** | 917 |
|---|---|---|---|---|---|
| 引擎耗时 | 14.4s | 15.0s | 15.6s | **96.3s** | 15.2s |

——是**每实例一次性**的，与参考音色是否换过无关（曾误判为 speaker cache，已排除）。

**这不止影响 indextts**：冷/热分离后还有两个模型有同样量级的首单惩罚——
`z-image`（冷 18~37s / 热 3.0~6.2s）、`hunyuan-image-3` i2i（冷 37s / 热 9.1s）。
`kr2` / `sensenova-u1.5` / `swiftvr` / `id4` 冷热一致，不受影响。

**修法：引擎层启动预热，钩子早就有了**。
`vllm_omni/entrypoints/openai/api_server.py:1194` 在启动时会
`await state.openai_serving_speech.warmup()` → `serving_speech.py:513` → `self._adapter.warmup()`。
但 `tts_adapters/base.py:236` 的默认实现是空的 `return`，**20 个 TTS 适配器里只有
`voxcpm2.py:79` 真正实现了**；`IndexTTS25Adapter` → `IndexTTS2Adapter` → `ARTTSAdapter` → `base`
一路继承下来就是空实现，所以启动时什么都没做。

`voxcpm2` 的实现约 30 行，可直接照搬：造一个合成 `OpenAICreateSpeechRequest` →
`server._generate_audio_bytes(...)` → 异常只 warning 不致命 → 记耗时。
它的 docstring 说明的理由与 IndexTTS 的情况一模一样：
*"CUDA Graph capture requires a vLLM ForwardContext … only available during inference.
The request also pays the one-time torch.compile cost"*。

**唯一的额外工作**：VoxCPM2 可以用 `voice="default"` 零样本预热，
而 IndexTTS 系必须有参考音色（该部署 `Loaded 0 supported speakers: []`，没有预置音色）。
预热请求需要自带一段极短的合成参考音（几百毫秒噪声即可，只为跑通 kernel，不需要好听）。

**在此之前的临时缓解**：实例重启后主动打一发预热请求；
延迟表按热态填（本文档 §2.1 已按热态重算）。

### 3.7 ✅ 已修复：`minimax-music3` 的对外 `task_type` 现在收 `t2m`

**现象**：发 `task_type=t2m` → 引擎 405 `Method Not Allowed`。因为
`t2m → kind "music" → POST /v1/tasks/music/` 是 ACE-Step 的路由，vLLM-Omni 没有这条
（只有 audio/audiogen/image/video 四条）。引擎侧对得上的是 `tts → kind "audio"`。

体验区一直是**前端**按引擎族改发 `tts`（`useMusicGeneration.js` 的 `resolvedTaskType`），
所以体验区没事；但直连 API 的调用方按能力标签「文生音乐」推出来的只会是 `t2m`，吃 405 且看不懂。

**修复**：改写收进网关层（`relay/channel/task/gpustackplus/adaptor.go`，
`BuildRequestBody` 里 task_type 白名单校验之后）：

```go
isMusic3 := common.MusicEngineFamilyForModel(...) == common.MusicEngineMinimaxMusic3
if isMusic3 && taskType == "t2m" {
    taskType = "tts"
    body["task_type"] = taskType
}
```

- 判据是**配置声明的引擎族**（`MusicModelConfig.models[].engine`），不是模型名 substring；
- 只改写 `t2m`：`cover`/`repaint` 同样落 kind "music"，但 Music3 本就不提供这两种玩法，
  改写成 tts 只会让引擎拿一个没有源音频的请求去合成，不如让它照旧失败；
- 原本在下面重复求值的 `isMusic3` 提前到这里复用，行为不变；
- 上线后前端那段特殊处理可以撤掉（一处改两处受益）。

回归测试 `music3_task_type_test.go` 三条，并做过回退验证（去掉改写立刻见红）：
`t2m → tts`、`tts → tts`（幂等，体验区现状不受影响）、
`ace-step 的 t2m 保持 t2m`（反向约束：它的引擎就在 /v1/tasks/music/ 上）。

**终局**：等 gpustack 侧让 `t2m` 也能指向 vLLM-Omni 之后，这段连同前端那段一起删。

## 4. 附：各玩法的客户端请求契约（实测跑通的形态）

统一端点 `POST /v1/videos`，`GET /v1/videos/{task_id}` 轮询，
`GET /v1/videos/{task_id}/content` 取成品。

| task_type | 必需输入 | 字段位置 |
|---|---|---|
| `t2i` / `t2v` | 仅 prompt | 顶层 `prompt`、`size` |
| `i2i` / `i2v` | 1 张图 | 顶层 `image` 或 `images[0]`（也认 `input_reference`） |
| `flf2v` | 2 张图（首、尾） | `images[0]`=首帧、`images[1]`=尾帧 |
| `r2va` | 参考图或参考视频 | `metadata.src_ref_images[]` / `metadata.reference_videos[]` |
| `sr` | 源视频 | `metadata.video` + `metadata.sr_ratio` |
| `tts`（情感合成） | 文本 + 参考音色 | `prompt` + `metadata.voice` |
| `tts`（声音设计） | 文本 + 声线描述 | `prompt` + `metadata.instructions` |
| `tts`（minimax-music3） | 歌词 + 曲风描述 | `prompt`=歌词 + `metadata.instructions` |
| `t2m` | 曲风描述 | `prompt`、`duration` |
| `cover` | 参考音频 | `metadata.reference_audio` |
| `repaint` | 源音频 | `metadata.src_audio` |

MiniMax H3 另有官方协议兼容层 `POST /v2/video_generation` +
`GET /v2/query/video_generation/{task_id}`，实测 6s/768P/16:9 用时 158s，
状态词是 `succeeded`（不是 `completed`）。

⚠️ **H3 的 `aspect_ratio` 由顶层 `size` 精确约分得出**，只接受
`21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16`。发 `1344x768` 会算出 `7:4` 被引擎拒；
要发 `1280x720` 这类精确比例。（引擎实际输出 1280×704。）
